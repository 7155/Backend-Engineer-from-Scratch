# 04 - 当前架构的收益、代价与停止升级条件

## 决策表

| 选择 | 主要收益 | 新成本 | 不值得引入的典型情况 |
| --- | --- | --- | --- |
| Headless/API-only | 多客户端、独立发布、技术栈解耦 | 网络失败、schema 兼容、跨仓库联调 | 单客户端、单团队、快速原型 |
| 多 Pod | 容量与实例级故障恢复 | stateless、连接预算、幂等、聚合日志 | 单实例已满足容量和 RTO |
| Celery/Broker | 请求与慢任务解耦、可重投 | 重复消费、DLQ、积压和监控 | 任务短且必须同步返回结果 |
| Redis/共享缓存 | 多实例共享派生数据、降低回源 | 陈旧、淘汰、热点与高可用 | DB 足够快或数据不可陈旧 |
| 行锁 | 保护复杂 read-modify-write | 等待、死锁、吞吐下降 | 原子 SQL/唯一约束已经能表达不变量 |
| Read Replica | 扩展读容量、隔离部分读负载 | 复制延迟、读己之写问题 | 主库读容量充足或必须强一致读 |
| OpenTelemetry | 跨进程因果与关键路径 | 采样、存储、CPU 和治理成本 | 单进程可稳定本地复现 |

## 为什么不是一开始就这样

架构机制只有在它降低的业务成本高于自身复杂度时才有价值。提前采用会让团队在需求和边界尚未稳定时，同时维护网络协议、异步状态、部署平台和故障恢复。

## 当前 Saleor 的判断

3.23.25 的 README 甚至直接承认：对单开发者、小业务、低流量且不要求 24/7 的场景，service-oriented 路线可能比传统一体化框架更复杂。这是“根据约束选择”，不是固定最佳实践。

## 面试 30 秒回答

我不会从组件名反推架构。先用最简单方案满足正确性，再用 QPS、P99、RTO/RPO、团队边界和真实故障触发升级。每次升级都要同时说明新增 owner、失败状态、运维成本，以及何时应该停止。
